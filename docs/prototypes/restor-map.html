Restor map — the containment problem, and Bruno's answer

The projects map is a third-party application inside an iframe. Its responsive behaviour belongs to Restor, and no stylesheet of ours reaches inside it. So this was never a responsive-design problem to solve; it is a containment problem — choosing how our page behaves around a component we do not control. Four options were proposed here. Bruno proposed a fifth, and it is the one we are building.

Your viewport: – px
Bruno's chosen solution

A dedicated full-screen page — give the iframe the whole viewport

A page of its own, on a blank template with no site header and no footer. The iframe is 100% wide and 100dvh tall, so Restor's application always receives exactly the dimensions its own responsive design was built for. A "Back to barlavento.eco" control returns the visitor: a floating pill on desktop, a full-width bar on a phone where a thumb needs a bigger target.

Every option below keeps our fixed-height box and negotiates with it. This one removes the box. That difference is why it wins:

  • The 960 px breakpoint stops mattering. Every other option is tuned to a number that belongs to Restor and moves whenever they ship a release. Not depending on it is better than measuring it accurately.
  • Only one scrolling context. Two competing scroll areas — the page and the iframe — is the worst thing you can do to someone on a phone, and neither B nor C had an answer for it.
  • Varying the height at breakpoints was already ruled out. Restor's three tabs — Overview, Sites, Connections — carry different amounts of content, so any fixed height is wrong for at least two of the three: one gets sliced, another gets a field of white space. Bruno's finding, and it kills that whole family of fixes on its own.
  • Tested on a real phone. iPhone 13, portrait — 390 × 844, the exact target width. The map works and the bottom bar obscures nothing; content scrolls past it. 100dvh rather than 100vh is doing real work here: mobile Safari collapses and expands its URL bar as you scroll, and the old unit measures against the wrong one. A desktop browser cannot show you that failure.

On a phone — 390 × 844, the exact case all four options below get wrong

That is the whole solution: no page around it, so nothing to slice. The back control is the full-width bar along the bottom — content scrolls underneath it, so it covers nothing.

On a screen wider than 640 px the same file drops that bar and puts a floating pill in the bottom-right corner instead. You are on a wide screen, so open it and you will see that version — there is no point showing you a shrunken panel here and calling it a desktop.

Provenance, and which copy is the real one. The design is Bruno Silva's, from issue #16. His blank WordPress page template on staging.barlavento.eco is the canonical implementation — it is the one that ships, and if the two ever disagree, his is right and this one is stale.

The file demonstrated above, restor-map-fullscreen.html, is that same pattern written as plain HTML and CSS. It exists to be read — his lives behind HTTP auth, so without this there is no version of the solution anyone can open, link to or quote. It is an illustration of a decision, not a source to build from. Most of what is prototyped here flows the other way — refined in this repository first, then carried into the WordPress site — but this one was solved in WordPress and written down afterwards, and pretending otherwise would just invite somebody to "sync" two files that were never meant to track each other. Two details are worth copying if the template is ever rewritten: the back control is a real href rather than history.back(), because a visitor arriving from a shared link has no history to go back through; and the mobile bar clears the iPhone home indicator via env(safe-area-inset-bottom).

Solutions proposed by Claude, rejected in favor of Bruno's

Kept in place rather than deleted, because the reasoning is the useful part: each of these accepts the fixed-height container as a given and then trades something away to live with it — a sideways scroll, a shrunken map, or a hole in the page on mobile. Seeing what they each cost is what makes it obvious that removing the container was the better move.

A — Fixed height, full width the original problem

What the sandbox did before this issue. Fine on a wide screen. Narrow the window and Restor switches to its mobile layout inside a frame whose height never changes, so the content is sliced. Resize this window to see the failure.

B — Minimum width, scroll horizontally works, costs a scrollbar

The frame is given min-width:1000px inside a horizontally scrollable container. The embed never sees a viewport below its breakpoint, so it never switches to mobile layout and nothing is ever sliced. The cost is a horizontal scroll on phones, which is a real usability compromise — and it is also the option that puts two scroll areas on the same page.

C — Aspect ratio box fixes slicing, not layout

Height follows width at 16:10, so the frame is never the wrong shape and nothing is cut off. But the embed still drops into its mobile layout below the breakpoint — it just does so in a correctly-shaped box. Solves half the problem, and the half it solves is the less annoying one.

D — Embed on wide screens, link out on narrow honest, but leaves a hole

Below 960 px the iframe is not rendered at all; a card links out to Restor's own site, which is properly designed for a phone. Nothing is ever broken, because nothing broken is ever shown. The cost is that phone visitors leave our page entirely — and Bruno's solution reaches the same destination without giving up on our own page to get there. Decided. Five containment strategies against the same embed, and the chosen one came from outside the list. Also settled on the way: Restor has no public API — their help centre says one is planned and being scoped, and there are no documented embed parameters beyond the iframe snippet — so the embed is the only door, and nobody needs to look again. What remains is the entry point that leads into the full-screen map, which is a design decision and Bruno's to make. Discussion belongs on issue #16 rather than in this file.
