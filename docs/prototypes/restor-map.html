Restor map — four ways of containing someone else's component

The projects map is a third-party application inside an iframe. Its responsive behaviour belongs to Restor, and no stylesheet of ours reaches inside it. So this is not a responsive-design problem to solve; it is a containment problem — choosing how our page behaves around a component we do not control. Four options below, honestly labelled.

Your viewport: – px Restor appears to switch to its mobile layout below roughly 960 px.

A — Fixed height, full width the current problem

What the sandbox does today. Fine on a wide screen. Narrow the window and Restor switches to its mobile layout inside a frame whose height never changes, so the content is sliced. Resize this window to see the failure.

B — Minimum width, scroll horizontally works, costs a scrollbar

The frame is given min-width:1000px inside a horizontally scrollable container. The embed never sees a viewport below its breakpoint, so it never switches to mobile layout and nothing is ever sliced. The cost is a horizontal scroll on phones, which is a real usability compromise — but a predictable one, unlike a sliced map.

C — Aspect ratio box fixes slicing, not layout

Height follows width at 16:10, so the frame is never the wrong shape and nothing is cut off. But the embed still drops into its mobile layout below the breakpoint — it just does so in a correctly-shaped box. Solves half the problem, and the half it solves is the less annoying one.

D — Embed on wide screens, link out on narrow honest, and least work

Below 960 px the iframe is not rendered at all; a card links out to Restor's own site, which is properly designed for a phone. Nothing is ever broken, because nothing broken is ever shown. The cost is that phone visitors leave our page to see the map — which is arguably correct anyway, since the map is Restor's application and not ours. Narrow this window past 960 px to see it switch.

Four containment strategies against the same embed. The choice is a design decision, not a technical one — each trades something different, and none of them can change how Restor's application behaves. Worth deciding deliberately: B keeps everyone on our page at the cost of a scrollbar; D is the least work and never shows anything broken; C is the smallest change from what exists today.
